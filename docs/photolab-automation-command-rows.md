# PhotoLab automation command rows and gates

Status: WP-G2 input, 2026-09-02. This document defines rows and gates; it does
not implement a second command table.

## Purpose and boundary

Decision-doctrine P11 requires one generated product command table to drive the
console vocabulary, automation protocol, agent exposure, and sync/async Python
clients. X3 requires UI/agent/Python parity, except that approval responses,
confirmation grants, filesystem-grant selection, and credential handling remain
user-only under ADR 0024. Per
`docs/builder-program/COORDINATION.md`, the Builder lane owns that one table.
PhotoLab supplies the rows below and the G-1/G-2/G-3 gates. WP-G1b consumes the
generated rows; it must not allowlist the private RPC names in this document.

The row shape mirrors the import-formats specification's **P11 command-table
exposure** section. `commandId` is an invocation identity, never another
operation name. Public filesystem-bearing schemas must replace today's raw
`path`, `sourcePath`, `destinationPath`, `artifactRoot`, and `checkpointPath`
fields with brokered grants before generation. The existing serde type and
wire-field lists below are evidence of today's operation payload, not permission
to expose raw paths.

Kinds are exactly **bounded query**, **long-running job**, and **canonical
transaction**. Trust classes are **project read**, **canonical write**,
**brokered filesystem read**, and **brokered filesystem write / externally
visible**. The last class requires a user approval for execution; the approval
response or confirmation token is structurally absent from automation.

## Command rows

Status values are **exists-as-private-RPC** when the operation is implemented
behind a renderer/IPC/private RPC, and **new** when the generated table must add
the operation. A private cancel or cleanup RPC belongs to its owning row; it is
not a second public command.

## User-only trust surfaces: no automation row

The following are status **user-only** and are deliberately absent from the
generated table and Python client:

- `products:export-confirm` consumes the short-lived overwrite token;
  `products:export-cancel` disposes that token. Automation may validate/start
  `photolab.products.export`, but it cannot confirm or deny the overwrite.
- The overwrite response inside Electron `reports:save` and project Save As is
  user-only. The generated export/save-as row can wait for the disposition but
  exposes no response method or token field.
- OS source/destination chooser activation and grant minting for project open,
  Save As, image/folder/HimmelCap/video/GCP/grid selection, product export, and
  report export are user-only foreground-window acts. Automation can request a
  passive grant card and consume only the resulting opaque grant.
- `ManagedAutomationApproval` responses and all `providerCredentials`
  operations are user-only. Agent/Python may observe sanitized pending/final
  disposition but cannot respond, mint a grant, or handle credentials.

The bridge-only window controls, preferences, workflow/preset editor files, and
panel visibility are application/view state rather than PhotoLab product
operations. They do not become raw filesystem RPC rows. If a workflow or preset
becomes canonical product data, it needs a separately specified canonical row.

## G-1 — every UI-reachable operation has a row

`apps/photolab/renderer/src/automationCommandRows.test.ts` imports the real
ribbon, enumerates every action id, and statically scans `App.tsx` plus every
`*Panel.tsx` for literal `photolab.*` calls. Every RPC must occur in the explicit
private-RPC-to-row mapping. Every ribbon action must map to a PhotoLab row, the
shared `io.import` row, or this documented view-local allowlist:

| Ribbon id          | Reason no product row exists                                                                   |
| ------------------ | ---------------------------------------------------------------------------------------------- |
| `automation.agent` | It shows or hides the shared Agent workspace; visibility is view-local.                        |
| `images.metadata`  | It opens a panel over the loaded image snapshot and changes no project state.                  |
| `batch.configure`  | It opens the local recipe editor; only explicit `photolab.batch.start` is a product operation. |

The test fails when a new renderer `photolab.*` string or ribbon action lacks a
mapping. The Electron allowlist also contains
`photolab.capture.image.prepare`, `photolab.capture.scale.evaluate`,
`photolab.gcp.observation.upsert`, `photolab.project.imageMask.cancel`, and
`photolab.jobs.status`; their rows/lifecycle mapping are included above even
though no current `App.tsx`/panel literal invokes them.

## G-2 — Python-client smoke before table completion

The Builder lane runs this smoke against the checked-in PhotoLab smoke dataset
using both the generated async client and, in a second process, its sync facade:

1. Open a fresh temporary PhotoLab project through a brokered destination grant.
   Inspect the dataset's image grant, assert a non-empty `PhotoImportBatch`,
   freeze the declared CRS decision, commit the images, and assert the committed
   entity count equals the inspected accepted-image count with no duplicate or
   invented coordinates.
2. Call `photolab.alignment.resolve`, then `photolab.alignment.start`. Poll only
   the generated status route to a terminal state. Assert kind `alignPhotos`,
   monotone progress, success, a published alignment entity, and matching frozen
   input/config hashes. Exercise validate before start and cancel on a separate
   disposable alignment request.
3. Import/commit the smoke GCP data, create the optimization snapshot, and start
   `photolab.gcp.optimization.start`. Assert kind `optimizeAlignment`, terminal
   success, the publication points to the exact alignment and snapshot hashes,
   and `latest` returns that publication.
4. Resolve inputs for the smoke product, start `photolab.products.start`, and
   assert its concrete `PhotolabJobKind`, terminal success, published dataset
   lineage (`sourceAlignmentEntityId`, GCP optimization id/snapshot, processing
   set when used, and mask-scope hash), content hash, and reopen visibility.
5. Close and reopen the project with fresh grants. Assert image ids/hashes,
   alignment, optimization, product lineage, and terminal job history are byte-
   equivalent. Assert neither client exposes raw `photolab.*` RPC dispatch,
   overwrite-confirm, approval-response, grant-minting, or credential methods.

The smoke runs before the Builder lane calls the generated table complete. A
private sidecar RPC smoke does not satisfy G-2.

## G-3 — generated console vocabulary

The generated table is the only console vocabulary source. Generation must emit
the proposed verbs above, their typed argument help, and aliases (if any) from
the same row revision used by automation and Python. The hand-listed `onCommand`
switch and fallback command string in `apps/photolab/renderer/src/App.tsx` are
removed after the Builder-owned table lands. A gate compares generated console
verbs, automation method ids, and Python sync/async methods row-for-row and fails
on a hand-added, missing, or stale PhotoLab command.
