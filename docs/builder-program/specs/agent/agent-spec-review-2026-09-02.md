Date: 2026-09-02  
Reviewed specification: `docs/builder-program/specs/agent/agent.md`

Disposition: **reject as specified** — 4 blockers, 10 major findings, 2 minor findings, 0 ideas

## Findings

1. **Severity: blocker. Contract question: B1 / ADR 0024 — can untrusted automation approve its own privileged operation?**

   **Objection.** The catalog defines `A` as both Agent and generated Python SDK (`agent.md:39`) and then gives that principal an `agent.approval.respond` command and an “A response” access path (`agent.md:48`). B1 repeats that approval is automation-respondable while a request is live (`agent.md:222–225`). This is not merely an imprecise surface description: it gives the same untrusted principal that requested an import/export authority the method needed to grant it. AG-D5's statement that harness-native approval cannot authorize product state (`agent.md:487–492`) does not cure the public command. ADR 0024 requires user approval and expressly says automation cannot bypass it by invoking a harness (`docs/adr/0024-automation-sdk-and-agent-trust-boundary.md:22–26`).

   **Proposed resolution.** Remove `agent.approval.respond` from the Agent/Python automation contract. Split the trust principals in the catalog: automation may query the pending request and observe its eventual disposition, but only a trusted product-UI IPC handler tied to the owning `BrowserWindow`, live foreground request, and actual user activation may confirm or deny. Bind the response to request id, exact plan hash, project generation, expected revisions, and a single-use nonce. Add negative schema/host tests proving that Agent, generated Python, scripted harnesses, replayed IPC, and a different window/session cannot respond. This follows X1 and ADR 0024; no owner choice is required.

2. **Severity: blocker. Contract question: A3 / B1 / registry cite-and-revise — which spec owns the public import command and interactive registration boundary?**

   **Objection.** The Agent spec publishes `io.import.execute` and low-level `registration.import.stage`, preview/session methods, and `registration.import.commit` to automation (`agent.md:377–389`). The owning import specification says the public verb is `io.import`, that `io.import.execute` remains an app facade, and that viewport-pick RPCs are rejected as unattended automation (`import-formats.md:567–575`). The Agent cross-spec table concedes that import-formats still “must amend” its decision and access sections (`agent.md:640–642`) while the Agent document presents itself as complete. That is exactly the second disposition forbidden by the program rule: a touched capability must be cited and revised in its owning decision record before the dependent spec is specified (`builder-program/README.md:43–52`).

   **Proposed resolution.** Reconcile the two documents in one change. Keep `io.import` as the public orchestration command. Permit bounded registration inspection/preview only through an explicitly user-owned, visible registration session; keep point acquisition in the owning import UI and return `needsUserInput` when it is absent. Commit through the owning `io.import` command rather than a separately exposed raw commit verb. Amend IF-D12/B1, the Agent matrix, generated schema naming, verification gates, and central registry together. If a lower-level method must exist internally, mark it app-private and make capability negotiation reject it for Agent and Python. This is derived from X3, ADR 0024, and the cite-and-revise rule.

3. **Severity: blocker. Contract question: B1 / builder-program registry — where are the Agent rows that make its access, naming, surface, and gesture claims authoritative?**

   **Objection.** `REGISTRY.md` says it was generated from seven finalized specs and names those seven; Agent is not among them (`REGISTRY.md:3–16`). A registry-wide search finds no central rows for `agent.workspace`, `agent.session`, `agent.turn`, `agent.approval`, or the grant surface. Section 5.4 still lists Agent as a pending domain with only three obligations (`REGISTRY.md:550–559`). The local catalog therefore has not undergone the required duplicate-act, shared-surface, gesture, state, or command-naming checks. This matters immediately because F8 already records unresolved camelCase-versus-snake_case automation naming (`REGISTRY.md:422–432`), while the Agent proposal adds both styles. Program status cannot be “specified” until its rows exist centrally and no open registry finding applies (`builder-program/README.md:43–56`).

   **Proposed resolution.** Add every Agent catalog row, grant/approval act, claimed gesture, shared persistent-island state, and automation method to `REGISTRY.md`; update its source count/status and Agent §5.4 disposition. Run the standing collision checks, apply the eventual F8 naming rule mechanically, and leave this spec drafted until all Agent registry findings are closed. This is procedural, not an owner decision.

4. **Severity: blocker. Contract question: A1 / D1 / E3 / AG-D12 — can the showcased “restore the last viewing box” workflow actually run deterministically with bounded context and bounded work?**

   **Objection.** The primary narrative asks `viewing_box.list` and then unspecified “bounded journal pages” to find the last activation (`agent.md:60–70,526–530`). The actual journal API pages only forward from `afterSequence` (`schemas/automation/himmelcad-automation-v1.schema.json:572–585`; `sdk/python/src/himmelcad/client.py:144–158`); it has no reverse, filter, or command-semantic query. Current journal entries contain only sequence, command id, kind, related id, and entity effects (`crates/himmelcad-core/src/canonical_document.rs:265–282`), so the Agent cannot identify an activation from the stated API without an unbounded history scan or an invented convention. The owning viewing-box spec says only “order by journal time” (`viewing-box.md:98–100`), not “most recently activated,” and separately says project reopen restores the active box exactly (`viewing-box.md:103–104`), contradicting the Agent story's ordinary reopen into a full model (`agent.md:62`). The promised compact built-in skill also has no exact id/content budget: a valid skill may be 256 KiB (`agent.md:121–134`), and G-AG-E2E asserts “one skill” but no total prompt-byte/token ceiling (`agent.md:587–592`). The flagship daily use case is therefore neither executable from the named contract nor protected from context spam.

   **Proposed resolution.** Amend the owning viewing-box decision first: add an indexed `lastActivatedSequence` to each surviving box or define `viewing_box.list(order: lastActivated, limit: 1)` with exact tie/deletion semantics. Then define the built-in artifact, for example `skills/builtin/restore-view-state/SKILL.md`, its exact minimal responsibility, and a small hard cap (recommended 4 KiB, with a measured token ceiling). Specify the exact call sequence and maximum calls/bytes: compact bootstrap → one indexed help result → one skill read → one bounded list query → one activate command; no journal scan and no full manual. Change the narrative to start after explicit deactivation, or state why the full model is present despite canonical reopen restore. Gate total injected bytes/tokens and calls as well as the final state. This follows X1, X2, P1, A3, and E3.

5. **Severity: major. Contract question: C4 / X3 — can a user undo an Agent's 40-command batch as the one action the Agent presented?**

   **Objection.** The spec provides attribution and says individual canonical commands enter the normal undo stack (`agent.md:248–251,511–514`), but it never defines a turn/batch undo unit. FP-D11 makes Ctrl+Z walk the most recent root command (`file-project.md:921–949`). Consequently, an Agent that presents one requested change implemented as 40 root commands requires 40 undos, may interleave with commands from another Agent session or the UI, and cannot offer a truthful “Undo Agent turn” action. Attribution is only half of X3 if the user cannot reverse the Agent at the unit in which it acted.

   **Proposed resolution.** Define a canonical `agentTurnId`/batch root. When the Agent plans multiple mutations as one requested result, validate all expected revisions and commit them as one all-or-none root transaction with child audit records; Ctrl+Z and an explicit **Undo Agent turn** affordance then compensate that root once. If an operation cannot be atomic, the preview must disclose the exact number of undo steps and it must not be labeled one batch. Define conflicts, cancellation, partial long-running preparation, concurrent-session serialization, and the C4 affected set. Amend FP-D11 by cite-and-revise and add a 40-command test that verifies one visible undo step and preservation of unrelated later fields. Derived from X3, X5, FP-D11, and C4.

6. **Severity: major. Contract question: C4 / X1 — what prevents prompts, provider echoes, and tool output containing secrets from becoming durable `.hcadx` history?**

   **Objection.** AG-D6 correctly keeps provider resume tokens local (`agent.md:494–499`), but the persistence contract archives finalized user/assistant transcripts and makes session deletion journaled and undoable (`agent.md:227–250`). Credentials are only one secret source: users paste API keys, private URLs, paths, client data, or access tokens into prompts, and providers can echo them. Current send logic inserts the raw prompt directly into the event stream (`ManagedAgentChat.tsx:175–198`). The future “secret redaction” test (`agent.md:569–573`) has no normative redaction boundary, secret classes, failure behavior, or durable schema. Calling Delete undoable also means it is not erasure from immutable objects/journal/history. The statement “never in `.hcadx`” is proven for provider bindings, not transcript-borne secrets.

   **Proposed resolution.** Define the persisted transcript schema and mandatory pre-persistence sanitizer. Never persist provider credentials, approval/grant nonces, raw canonical paths, bulk lease tokens/content, hidden reasoning, or marked sensitive prompt spans; store display basenames and typed redaction records instead. Apply the boundary to user input, provider output, errors, command previews, and console projection before immutable-object creation. Tell the user that ordinary Delete is recoverable through undo. If secure purge is offered, make it a separate maintenance operation that names archive/history/backup limits and performs reachable-object compaction; otherwise do not imply erasure. Add pasted-secret, echoed-secret, malformed-event, archive inspection, undo, and export/save-as tests. This is required by X1 and ADR 0024.

7. **Severity: major. Contract question: B2 / E2 / ADR 0024 — can an Agent repeatedly summon native pickers or approval UI without a fresh user gesture?**

   **Objection.** B1 says `automation.grants.request` “always causes a user-owned OS picker/card” (`agent.md:373–375`), while the narrative says an inline card appears and the user's press opens the picker (`agent.md:146–150`). Those are materially different trust and lifecycle contracts. Under the former, a looping or compromised harness can repeatedly open native pickers, steal focus, and create an unbounded pending-request queue. B2 allows pending requests to survive a closed card until expiry/session end (`agent.md:391–393`) but defines no coalescing, foreground ownership, request ceiling, or background behavior.

   **Proposed resolution.** Make `automation.grants.request` create or reuse a passive, idempotent pending request only. Native picker opening must require a trusted, foreground user click on that exact card; automation cannot synthesize it. Permit at most one active picker and one pending request per `(session, capability, purpose)`, coalesce duplicates, rate-limit repeated denials/cancels, and define hide, window blur, project close, provider death, and expiry outcomes. Add abuse tests proving no modal/picker opens from an automation call alone and queue memory stays bounded. Derived from X1, B2, and ADR 0024.

8. **Severity: major. Contract question: C3 / E2 / X1 — does “canonical path identity” actually prevent path substitution between approval and use?**

   **Objection.** The spec says the host resolves a grant to a canonical path immediately before forwarding and the sidecar receives that path (`agent.md:405–407,423–428`). A canonicalized pathname is not a frozen file identity. A symlink target, mount, directory entry, or destination file can change after grant/plan validation and before open/rename; resolving “immediately before” narrows but does not close the race. The 40×50 GB extreme magnifies the window. The export contract similarly freezes collision information but does not require revalidation against the opened destination parent at publish time.

   **Proposed resolution.** Source grants should bind an OS-opened read handle or platform file identity plus expected metadata/hash policy and use no-follow semantics; pass a brokered handle/lease to the sidecar rather than a re-resolved raw path. Destination grants should bind the opened parent/target identity, revalidate collision state at execution, create the temporary sibling through that directory handle, flush, and atomically rename with explicit no-clobber/replace semantics matching the accepted plan. Reject identity change and force re-plan/reapproval. Test symlink swap, rename swap, mount replacement, and target creation after approval on supported platforms. Derived from X1 and ADR 0024.

9. **Severity: major. Contract question: E3 / documentation drift — is the per-domain capability page a mechanically derived build artifact or prose behind a still-valid anchor?**

   **Objection.** AG-D3 rejects a hand-written manual and says a manifest “points” to catalog/contract/decision anchors, with changed/missing anchors failing (`agent.md:474–479`). It does not define what source fragment is extracted, whether prose is generated or copied, how semantic changes with the same anchor are detected, or where the checked artifact/manifest lives in the repository. G-AG-DOC mutates a fixture anchor only (`agent.md:577–579`); an author can change approval posture or state semantics without renaming the anchor and leave the capability page stale. `/workspace/docs/domains/<domain>.md` is a runtime projection, not by itself an E3 source/build artifact.

   **Proposed resolution.** Make capability documentation an explicit checked build output from machine-readable blocks in each Builder spec (or a deterministic normalized source-section extractor). Check in or reproducibly generate a manifest containing source path, section id, normalized source-fragment hash, schema hash, generator version, and output hash. The gate must fail on same-anchor content changes, command/access/approval changes, omitted domains, and hand edits; package verification must compare the projected files to those hashes. State plainly that domain capability prose is generated and cannot be separately authored. This follows X3, FUNCTION-CONTRACT auditability, ADR 0024's SDK staleness rule, and E3.

10. **Severity: major. Contract question: E2 input arbitration — what happens when the armed mention tool receives a double-click on void/bare cloud or each touch extreme?**

    **Objection.** The gesture table says a single click on void/bare cloud leaves the tool armed (`agent.md:283–284`), then says every double-click's first click consumes/disarms (`agent.md:285`). Both cannot be true for the same first click. The platform gives double-click on void/cloud the distinct meaning “clear selection” and allows a tool to claim it only with a stated reason (`ui-platform.md:539–553`); the Agent table neither preserves nor claims that case. Touch collapses tap into one row and omits tap-again and double-tap, despite the platform defining separate deselect/clear meanings. AG-D11's claim that the table is exhaustive (`agent.md:521–524`) is therefore false.

    **Proposed resolution.** Split double-click entity from double-click void/cloud. Recommended: entity click inserts/disarms and suppresses a second activation in that click sequence; void/cloud double-click remains platform-owned and clears selection while the mention tool stays armed, unless a documented reason justifies a claim. Enumerate tap, tap-again, tap-hold, and double-tap separately, including whether each leaves the tool armed. Add browser tests for every row and update the central gesture registry. Derived from E2 and UIP §3.6.

11. **Severity: major. Contract question: C2 extreme-class member — what exactly is the “named selection query reference” used above 1,000 entities?**

    **Objection.** The spec caps chips at 1,000 and substitutes a named selection query reference above that (`agent.md:239–242`), but no such type, command, lifecycle, persistence rule, resolver, page format, or stale/deleted behavior exists in the catalog. It is unclear whether the reference captures exact ids/revisions or remains a live query that silently changes with selection. The latter contradicts the stable-reference rule in AG-D8; the former can itself be huge and needs bounded storage/query behavior. The largest mentioned entity is a point cloud, but the largest selection-set member—the class that triggered this special path—is not actually specified.

    **Proposed resolution.** Define a discriminated captured-selection reference and its owner command, for example `agent.reference.capture_selection`. It should freeze exact ids and observed revisions into an immutable, digest-addressed set; expose bounded pages and aggregate stale/deleted counts; declare project/session lifetime, archive/undo policy, display name, permission checks, and behavior when selection changes. Never substitute a live selection implicitly. Add 1,001- and 100,000-entity tests for memory, prompt bytes, paging, deletion, and restart. Derived from C2, E2's extreme rule, X1, and AG-D8.

12. **Severity: major. Contract question: X3 / A3 / format evolution — where is the canonical journal attribution schema and migration that AG-D9 depends on?**

    **Objection.** The visual criteria require a canonical journal fixture containing session/turn actor data (`agent.md:611–615`), and §6 says all Agent calls will emit attribution consumed by the journal (`agent.md:550–556`). Current `CanonicalJournalEntry` has no actor field (`canonical_document.rs:265–282`). The spec correctly labels attribution as future work, but its implementation delta does not name the canonical core type, archive/serialization version, deterministic hashing, undo/redo propagation, replay behavior, migration of old entries, or privacy-safe actor representation. Referencing the aspirational `PROJECT-FORMAT.md` actor field is not a code-backed A3 implementation plan.

    **Proposed resolution.** Specify the exact versioned actor record—origin enum, stable local session/turn ids, display label policy, no provider secret/thread token—and add it to the canonical transaction/journal contract. Define how forward, undo, redo, replay, archive load/save, old entries, Python models, console, and sibling apps consume or ignore it. Include migration/backward-compatibility and deterministic-serialization tests. Keep attribution even when a session is deleted, but detach sensitive transcript content. Derived from X3, A3, C4, and PROJECT-FORMAT's canonical-authority rule.

13. **Severity: major. Contract question: E2 passive consumers — what do PhotoLab and other sibling apps do when the shared protocol and project Agent data change?**

    **Objection.** E2 names “sibling apps consuming the shared automation schema” and then asserts each sees the exact effects in the Agent workflows (`agent.md:270–273`); the I/O section only names PhotoLab as a client consumer (`agent.md:423–425`). No per-app semantics are stated for unsupported Agent methods, capability negotiation, project Agent data preservation, archive round-trip, generated-client changes, or UI absence. A sibling that opens and saves a Builder archive could discard unknown Agent product data; a shared schema client could advertise or route commands its app does not support. “Sibling apps” is a category, not the required passive-consumer enumeration.

    **Proposed resolution.** Enumerate each shipping sibling app/package that reads the project format, shared schema, or `@himmelcad/app` clients. For each, specify: capability absent/present, routing behavior, whether Agent UI exists, preservation of unknown Agent product data on open/save/export, and generated-client/build-gate impact. Require fail-closed negotiation for unsupported methods and round-trip preservation tests for `.hcadx`. Apply the shared behavior where the domain allows it; record explicit non-adoption elsewhere. Derived from E2, A3, SYSTEM-001, and the repository's sibling-app principle.

14. **Severity: major. Contract question: E2 / session persistence — what is the crash-consistent commit boundary for finalized transcript chunks and session deletion/restore?**

    **Objection.** The spec moves renderer events to main-owned chunked project data and promises restart rehydration (`agent.md:178–182,248–250,550–552`), but “finalized” is not a storage protocol. It does not define chunk identity/order, duplicate provider events, atomic session-index plus object publication, acknowledgement cursors, a crash between object write and journal/index update, delete-versus-running-turn races, or how undo of deletion restores the exact transcript while a provider thread is unavailable. D2 also says finalized messages are never dropped (`agent.md:258–261`) without a retention/storage limit or failure response when the project cannot accept more data.

    **Proposed resolution.** Define an append protocol with immutable chunk ids/content hashes, monotone per-session sequence, provider-event idempotency keys, bounded chunk size, and atomic publication of object plus session head through the project store. Specify recovery for orphan objects and missing heads, disk-full behavior, the finalization point visible in UI, delete/end/turn serialization, undo affected set, and retention policy that never silently deletes. Add kill-point tests at every publication phase, duplicated/out-of-order event tests, deletion during a turn, and archive round-trip. Derived from X1, P1, C4, and SYSTEM-001.

## System feedback

Two parts of the governing system failed to force a sufficiently precise answer.

1. **FUNCTION-CONTRACT B1's single `A` automation bucket is too coarse for approval systems.** It asks whether Agent and Python can reach a command but not which trust principal may complete a user-authority transition. That allowed `agent.approval.respond` to look like parity while violating ADR 0024. B1 should require principal-level reachability for security-sensitive commands: Agent harness, generated Python, trusted renderer UI, Electron main, and sidecar—not just “automation.”
2. **Doctrine X3's parity wording did not force reversal at the action unit presented to the user.** The spec achieved common commands and attribution but still omitted the user's inverse for a multi-command Agent turn. X3 should explicitly require that an Agent-presented batch has a truthful, user-reachable undo/compensation unit, or that the UI disclose it is multiple steps.

The other contract questions and doctrine axioms did their jobs: A3 plus cite-and-revise exposed the import contradiction; C4 exposed batch/transcript restore scope; E2 exposed gesture, path-race, and passive-consumer gaps; E3 exposed the documentation staleness gap; and X1/X2 made the approval, security, and context-budget failures non-tunable.
