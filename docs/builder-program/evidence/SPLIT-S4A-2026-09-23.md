# Split step 4a evidence — document and transform crates

Date: 2026-09-23 (Europe/Berlin)

## Result

Step 4a creates the foundation crates `himmelcad-document` and
`himmelcad-transform`. The clean document state, canonical JSON, entity-command,
project DTO, durable-filesystem and atomic-publication modules moved to document.
The transform contracts, pure geometry algorithms, generic CRS declarations,
grid codecs and site-calibration reader moved to transform.

Core and sidecar re-export every moved module at its former public path. The
frozen protocol corpus is byte-identical, the automation schema golden passes,
and the PhotoLab project-file contract passes. No schema, serde attribute,
field order, default, algorithm, file format or wire contract changed.

The stateful canonical store, mixed project archive and process-owning transform
runtimes remain in sidecar for the dependency reasons recorded below. Moving
them in this step would require contract extraction or the process/job work that
is explicitly reserved for Step 4b.

## What stayed and why

- `himmelcad-sidecar::canonical_project_store` stays whole. Its durable import
  publication API directly owns `himmelcad_io::{CanonicalImportPackage,
CanonicalJsonObject, CanonicalPreparedDataset, CanonicalResourceSet,
ProviderContractError}`. `himmelcad-io` still imports mixed core/domain
  contracts. Moving the store would therefore form the Cargo cycle
  `document -> io -> core -> document`. The correct later cut is to extract the
  provider/package contract downward or split the import-publication adapter;
  either is contract surgery outside this behavior-preserving step. The store's
  journal-last order, ready marker, fsyncs and recovery code remain unchanged.
- `himmelcad-sidecar::project_archive` stays whole. Archive extraction accepts
  both the canonical manifest and a directly deserialized
  `PhotolabProjectManifest`, including the PhotoLab format-version gate.
  Separating generic archive I/O cleanly needs an injected manifest validator
  and corresponding test/API migration. That is behavioral/interface surgery,
  so the complete module remains in sidecar.
- `crs_runtime` stays because it directly owns `ProcessGroupDropGuard`, calls
  `process_group`, and consumes the PhotoLab job `CancellationToken`.
- `transform_runtime` stays because it configures child processes through
  `process_group` and consumes the same job cancellation contract.
- `crs_service` stays because it owns a service cache around `crs_runtime` and
  consumes job cancellation.
- `transform_geometry_runtime` stays because it composes
  `transform_runtime` and job cancellation. Moving these four modules before
  process groups and generic job contracts move in Step 4b would create a
  transform-to-sidecar dependency or duplicate lifecycle policy.

No job supervisor, process-group or worker code moved in Step 4a.

## Cycle cuts

- `transform <-> transform_geometry`: `CirclePolicy`, `TextScalePolicy`,
  `DensifyPolicy` and `GeometryTransformPolicy` now live beside
  `TransformSpec.geometry_policy` in `transform`. `transform_geometry`
  re-exports the four types at their old path and depends one-way on
  `transform`.
- `pointcloud_export <-> product_export`: the existing backup/rename/restore
  `publish_replace` implementation moved verbatim from `product_export` into
  document `publish_fs`. Product, point-cloud and camera export now call the
  shared helper through the sidecar compatibility path. The former
  point-cloud-to-product-export edge is gone.
- generic CRS versus PhotoLab policy: product-neutral CRS/epoch/height/grid/
  operation-selection declarations live in transform; the PhotoLab import
  decision and validation workflow stays in core.
- core/sidecar compatibility: core depends downward on document and transform;
  sidecar re-exports document filesystem and transform grid/calibration modules.

## Crash-safety preservation

`canonical_document`, `canonical_json`, `durable_fs` and the existing
`publish_fs` production code moved without production logic changes. The atomic
replacement helper retains this exact sequence: remove stale operation backup;
rename the existing destination to backup; rename the completed temporary path
to destination; restore the backup if publication fails; remove the backup
after success. Store journal/manifest write-ahead ordering did not move because
the store remains whole.

Coverage that exercised these boundaries includes document fs tests, all
canonical store recovery/publication tests, project archive cancellation and
overwrite tests, point-cloud/product/camera export tests, PhotoLab project-file
contracts, the frozen response corpus, and the supplemental serialized sidecar
library run.
