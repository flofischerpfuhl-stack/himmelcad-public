# Split step 4b evidence — kernel mechanics and transform runtimes

Date: 2026-09-23 (Europe/Berlin)

## Result

Step 4b moves the process containment implementation and runtime-neutral job
contracts into the new foundation crate `himmelcad-process`, exposes those
contracts through `himmelcad-command`, moves worker-toolchain admission and the
generic supervisor/admission half of `job_runtime` into `himmelcad-command`, and
moves all four remaining transform runtimes into `himmelcad-transform`.

The lower process crate is necessary because transform is a foundation module
and must not depend on the command layer. `cargo tree -p himmelcad-transform`
contains `himmelcad-process` and does not contain `himmelcad-command` or
`himmelcad-core`. `himmelcad-command::process_group` remains the command-layer
public owner through a re-export, while `himmelcad-sidecar::process_group`
remains the compatibility path.

The remaining frozen CRS decision/audit contract also moved from core to
transform. This was the smallest cycle cut for `crs_service`: core already
depends on transform, so transform could not consume core's
`ImportTransformationDecision` and `FrozenImportTransformation`. Core re-exports
the complete module at its old path.

No serde attribute, field order, default, error text, scheduling algorithm,
process-group behavior, cancellation poll, progress coalescing rule, checkpoint
commit rule, drain deadline, wire route, or protocol response changed. The
frozen route/response corpus is byte-identical.

## What stayed and why

- PhotoLab memory planning, extraction/matching fallback policy, raster
  preparation memory policy, stage labels, stage kinds and product job kinds
  remain in `himmelcad-core::photolab_jobs` and the retained PhotoLab half of
  `himmelcad-sidecar::job_runtime`. They belong to the photogrammetry domain and
  move in Step 5.
- `himmelcad-sidecar::job_runtime` retains 2,532 lines: 670 production lines of
  PhotoLab memory policy, the command compatibility re-export, and the existing
  combined tests. The tests intentionally remain together because they exercise
  the unchanged boundary between PhotoLab policy and supervisor mechanics. Test
  bodies, scratch paths, temporary directories and timing bounds are unchanged;
  test-only edits are import paths/lists.
- The command supervisor still consumes the existing PhotoLab job record and
  admission evidence types. Generalizing that persisted record belongs with the
  Step 5 domain split; duplicating it here would change type identity and risk
  wire drift.
- No requested transform runtime retained sidecar-only state. All four moved.

## Process/cancellation crate choice

`himmelcad-process` is a foundation crate containing only runtime-neutral job
contracts and external-process containment. It depends on model solely for the
existing `ObjectHash` checkpoint fields. Core depends on it to preserve the old
PhotoLab paths; transform depends on it for `CancellationToken` and
`process_group`; command depends on it and re-exports process containment.

This placement preserves the required direction:

```text
command -> core/transform/process
transform -> model/process
core -> document/model/process/transform
```

There is no `transform -> command` or `transform -> core` edge.

## Compatibility paths and remaining consumers

Compatibility re-exports exist at every former public path:

- `himmelcad-sidecar::{process_group,worker_toolchain,crs_runtime,crs_service,transform_runtime,transform_geometry_runtime}`;
- `himmelcad-sidecar::job_runtime` for every moved supervisor/admission symbol;
- `himmelcad-core::photolab_jobs` for cancellation, progress and checkpoint
  contracts;
- `himmelcad-core::photolab_crs` for the complete moved CRS decision contract;
- `himmelcad-command::process_group` over the lower foundation implementation.

Remaining compatibility consumers are deliberately unchanged:

- sidecar `process_group`: `brush_runtime`, `capture_runtime`, `colmap_runtime`,
  `dedode_runtime`, `dense_raster_prep`, `mvs_runtime`, `mvs_scene`,
  `raster_runtime`, and `main`;
- sidecar `job_runtime`: `brush_runtime`, `colmap_runtime`,
  `dense_raster_prep`, `mvs_runtime`, `raster_runtime`, `main`, and the binary
  `project_runtime`;
- sidecar `worker_toolchain`: `main`;
- sidecar `crs_runtime`/`crs_service`: `main`; the two transform-runtime
  compatibility exports currently have no remaining Rust consumer outside the
  sidecar export itself;
- core `photolab_jobs`: PhotoLab/domain implementations throughout sidecar,
  including the portable-MVS binary and fixture example; direct generic progress
  consumers remain `project_runtime` and `raster_runtime`, while cancellation
  remains used by the worker/runtime modules;
- core `photolab_crs`: core `photolab_project` and `product_import_package`, plus
  sidecar `gcp_runtime`, `image_commit`, `main`, and `project_runtime`.

Migrating these call sites is unnecessary for proving type ownership and is
deferred to Step 5.
