gate, 3D→2D→3D remains FAIL by 1.8 ms**.

The fixture, camera paths, adapter and target were not changed to obtain the

## Step 1 — diagnosis before behavioural changes

The V-01 frame ring was extended with observational fields for worker decode,
main-thread artifact ingest, hierarchy application, upload time/bytes/tiles,
LOD visibility changes, JS heap, WASM linear memory/growth and interval time not
accounted for by synchronous frame CPU. `viewer-baseline.mjs` correlates those
fields with `PerformanceObserver("longtask")`, samples
`performance.measureUserAgentSpecificMemory` when exposed, and retains the 20
worst frames and a histogram per run. Chromium did not expose the specific
memory API in this Electron session, so boundary samples report
`supported:false`; `performance.memory` and exact WASM page counts remained
available. GPU timestamp queries are unsupported on this WebGL2 adapter, so GPU
time stays `null` rather than being fabricated.

The quantitative hypothesis was therefore **not uploads, hierarchy decode,
LOD swaps, WASM growth or a GC burst**:

- across the median orbit, maximum per-frame upload, hierarchy work, decode
  ingest and WASM growth were all zero; one worst frame changed four LOD
  visibilities, while the other 19 changed none;
- synchronous CPU submit was 0.8–1.6 ms and total frame CPU 13.3–26.7 ms, but
  the unexplained interval was 104.0–155.2 ms;
- JS heap ranged 53–89 MB across before runs without WASM growth. The renderer
  trace's longest renderer-thread GC event was 12.52 ms, too small to explain
  the 100–181 ms population;
- long-task p95 was 85.5 ms in orbit run 1. A bounded CDP trace
  (`viewer-baseline-2026-09-09-v07-trace.trace.json`) found 112 renderer
  `FunctionCall` events above 33 ms in React's `performWorkUntilDeadline`.
  Representative nested work was App render 43.5 ms, React render 52.3 ms,
  commit 36.1 ms and `ParseHTML` 14.9 ms.

The trace and a 25 ms code cadence converged on the cause: durability polling
published a new, equal object every tick, forcing the complete Builder App to
render around 40 times per second. A separate one-second jobs clock also lived
in App. These periodic shell renders, not the settled streaming frontier,
created the frame tail.

## Step 2 — fixes and same-path measurements

1. The window-mask viewport now applies the governor's existing
   `runtimeQuality.renderScale` to its physical backbuffer. It previously
   exposed scale decisions in telemetry but always allocated the full native
   surface. The intermediate five-run medians were orbit/pan/zoom/fly
   `139.3/134.4/137.5/136.0 ms` and transition `164.9 ms`; GPU allocation fell
   from about 76 MiB to 44 MiB. This was real but not the dominant fix.
2. The one-second jobs clock moved into the two small live jobs surfaces.
   Durability polling now publishes only a semantically changed status, while
   continuing to read every 25 ms. Its focused gate measured acknowledgment
   p95 `24.322 ms` and exactly one publication for stable samples. The first
   five-run capture after isolating only the jobs clock still measured
   `134.0/133.3/140.3/136.2/159.0 ms` medians, confirming it was secondary.
   The first diagnostic capture after durability deduplication measured
   orbit/pan/zoom/fly at
   `18.5/19.4/20.4/20.2 ms` p95 and transition at `29.5 ms` p95.
3. Navigation-mode settlement moved to a tiny external subscription consumed
   only by the ribbon and viewport bottom bar. It no longer invalidates the
   whole Builder App after the blend. The single-run transition validation
   changed from `32.8 ms` immediately before this isolation to `27.2 ms` p95;
   its maximum fell from `125.8 ms` to `56.0 ms`.
4. VC-D10 target-LOD prewarm now feeds the transition endpoint into the
   existing auxiliary streaming selector before the blend. Command
   orchestration waits for two quiet presented frames, but presenting frames
   never wait for streaming: every request/decode/upload still executes through
   V-03's ordinary per-frame caps. A new mode request aborts the old prewarm.
   On this already-resident fixture the prewarm correctly scheduled zero new
   bytes and swaps; the adjacent one-run transition values were `29.5 ms`
   before and `32.8 ms` after (ordinary run variance, both within target), so
   V-07 does not claim a warm-frontier speedup from a case that needed no I/O.
