# Rust sidecar/core split and hardware profile plan

**Evidence date/revision:** 2026-09-23, `main` at `8d9cdc3`. This is read-only analysis; only `cargo metadata --format-version 1 --no-deps` was run, with `CARGO_TARGET_DIR=/media/oem/ZusatzSSD1/himmelcad-target/analysis`. No build was run.

## Baseline and dependency cuts

`himmelcad-core` is 39,102 Rust lines and `himmelcad-sidecar` 116,416. `sidecar/src/main.rs` is 13,619 lines; its production section contains **159** route literals at this revision (79 `photolab.*`), versus ADR 0032's earlier 152. `main.rs:1630-1800` first routes by prefix, then 13 handler `match` blocks; `main.rs:12283` begins tests. `sidecar/src/lib.rs` publicly declares 49 top-level modules; `grid_codecs::ggf` and the binary-only `mod project_runtime` bring the module sources to 51, plus `main.rs` itself.

A lexical scan of `crate::…`, `himmelcad_core::…`, and `himmelcad_sidecar::…` found 88 unique edges among 36 core modules and 323 among 52 sidecar modules (including the binary). The high-fan-in nodes are `core::hash` (23 core/31 sidecar users), `core::entity_model` (11/12), `core::photolab_jobs` (28 sidecar users), `sidecar::process_group` (11), and `sidecar::job_runtime` (8).

The Architecture table is wrong in four material ways: `mesh_surface` is a surface algorithm, not model; `photolab_jobs`/most of `job_runtime` are domain policy, not generic jobs; `project_runtime` is PhotoLab domain storage, not the shared document; and prepared artifact/hierarchy contracts are missing. Also, “kernel owns project store” conflicts with the table: kernel should own a `DocumentService` handle, while the implementation belongs to document. `himmelcad-io -> himmelcad-render` proves prepared wire types currently sit too high. GPU calibration execution must remain a thin renderer adapter, although its observations/policy belong to hardware profile.

## Dispatch, products and wire compatibility

Use an explicit builder, not linker inventory or a new dependency. `RpcModule::register(&self, &mut CommandRegistry)` installs exact method strings and handlers returning `Pin<Box<dyn Future<Output=RpcResponse> + Send>>`. Duplicate registrations fail startup. `BuilderContext` exposes only document/jobs/worker capabilities. Each product binary explicitly calls `register()` for selected domains; the registry preserves current request structs, serde attributes, top-level response structs, error codes and the single existing serialization/write path. Unknown methods remain `-32601`.

First wrap today's prefix/match dispatcher as one legacy module and add a golden route inventory; then move one exact route family at a time. Extend `scripts/generate-command-table.mjs` to emit a Rust catalog from `schemas/automation/himmelcad-automation-v1.schema.json`; module registration tests must equal the product-filtered sidecar catalog, with a named allowlist for non-command transport routes. The Python generator remains schema-driven. Add a differential test that serializes old and registry responses for deterministic/error fixtures byte-for-byte before deleting the old path.

Choose **two binary crates**, `himmelcad-builder-sidecar` and `himmelcad-photolab-sidecar`, not feature flags. Builder links document/IO/registration/point-cloud/surface/raster/drafting; PhotoLab links document/IO/registration/photogrammetry/raster plus required output services. Separate roots make accidental domain linkage visible in `cargo tree`, avoid feature-unification leakage, and produce independently hashable release artifacts. Shared crates still reuse compilation; final LTO runs twice, but Builder becomes materially smaller/faster to link while PhotoLab remains similar. Package each under the installed name `himmelcad-sidecar[.exe]`.

Update both app `package.json` scripts, four electron-builder YAML files, `.gitlab-ci.yml`, sidecar path tests, `build-photolab-windows-rust.mjs`, `stage-photolab-runtime.mjs`, release/smoke scripts and `check-photolab-release-inventory.mjs`. Portable MVS stays PhotoLab-only.

## Hardware profile

Current decisions are split as follows; PhotoLab has no persisted Electron fallback equivalent.

| Location                                                  | Hardware decision today                                                                                                                                                                                                                                                                                            |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `render::hardware_policy` (1,693 lines)                   | Uses 60% reported/fallback VRAM, split 55% buffers/35% textures/10% staging; 20%/10% system RAM decoded/compressed; `logical cores − 2` decoders (1–16), 2× requests (4–32); device-kind fallbacks, measured I/W/D classes, MSAA/transparency, mobile caps, and hysteretic quality governor.                       |
| `render::gpu_calibration` (473) and WASM/viewer           | Three completion-fenced samples each for 8 MiB upload, points, triangles and splats; browser supplies `deviceMemory` and `hardwareConcurrency`, recalibrates policy, and automatic backend probing rejects a fallback WebGPU adapter in favor of WebGL2.                                                           |
| `sidecar::hardware_runtime` (216), core `photolab_models` | `/proc` or WMIC RAM/cores; AVX2; `nvidia-smi` CUDA/name/VRAM; `vulkaninfo`; model backend order CUDA→Vulkan→CPU and 16/8/4 GiB tiers for tile/batch/concurrency.                                                                                                                                                   |
| `main.rs`, core jobs, `job_runtime`, `dense_raster_prep`  | Job concurrency `ceil(physical cores/2)`, clamped 1–8, queue 64; 8 GiB probe fallback; usable RAM subtracts max(4 GiB, 12.5%); measured extraction/matcher/GDAL byte models, stage shares, tiling/quality fallback, concurrent reservation, cgroup `MemoryMax` or `prlimit`, peak recording and typed OOM failure. |
| Electron/viewer                                           | Builder persists WebGPU→WebGL2→SwiftShader recovery, forces D3D11 on Windows hardware mode and enables unsafe WebGPU only for Linux dev; both BrowserWindows enable WebGL. `KernelViewerSession` retries each backend, reports fallbacks and device-loss recovery.                                                 |

`himmelcad-hardware-profile` should own identity, inventory, capability/calibration observations, compute/render budgets and deterministic quirk resolution without depending on wgpu or domains. Render retains only the benchmark runner. A pure `@himmelcad/hardware-profile` TS package accepts injected Electron/browser facts and returns launch switches/status; both hosts use it.

Store reviewed rules in `hardware/quirks-v1.json`: `{id, priority, match:{os,vendorId,deviceId,driverMin,driverMax,backend,sessionType,electronRange}, actions:{disableBackends,forceAngle,renderBudgetScale,computeBudgetScale}, reason, expires}`. Require stable IDs/ranges, deterministic priority, conflict rejection, bounds, tests, and no free-form GPU-name matching.

The Builder chip at `App.tsx:4939` is currently inferred from “not persisted software.” Replace it with live state from Electron GPU feature/identity facts plus the successful `KernelViewerSession` backend/adapter (`isFallbackAdapter`). States: Initializing, WebGPU hardware, WebGL2 hardware, Software (SwiftShader), unavailable. Never label hardware until the selected adapter reports it.
