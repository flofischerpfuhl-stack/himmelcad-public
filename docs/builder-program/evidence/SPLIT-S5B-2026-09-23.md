# Split step 5b evidence — point-cloud, surface, and registration domains

Date: 2026-09-24
Repository revision at start: `8b480025` (`main`)
Result: the point-cloud, surface, registration, shared SMRF, and dense-raster
implementations have named owners with no domain-to-domain Cargo edge. Route
dispatch and its frozen protocol remain in the legacy sidecar registry.

## Resulting placement

The production dependency direction for this cut is now:

```text
sidecar composition / legacy registry
  -> himmelcad-domain-pointcloud
  -> himmelcad-domain-surface
  -> himmelcad-domain-registration
  -> himmelcad-domain-raster

each domain -> document / IO / model / prepared / process / spatial foundations
```

No domain crate depends on another domain crate. Surface sampling reaches the
point-cloud implementation only in the sidecar adapter for
`SurfaceDocumentCommands`; the surface crate sees the neutral request/result
contract and injected document capability only.

`ground_classification` belongs in `himmelcad-spatial`, rather than a new crate,
because SMRF is a bounded spatial morphology/classification algorithm consumed by
both point-cloud and raster preparation. The existing spatial crate already owns
the lower spatial algorithms and depends only on process/serde foundations. A new
foundation crate would add a package boundary without removing another edge.

`dense_raster_prep` belongs in `himmelcad-domain-raster`: it is raster preparation
policy and execution, not a renderer-neutral prepared-data contract. The PhotoLab
memory coupling is now the injected `RasterMemorySink`; the sidecar job adapter
implements that contract. Upper job-manager tests stay behind the old compatibility
path, so raster has no dependency back to PhotoLab command/runtime code.

## Canonical application runtime decomposition

`canonical_app_runtime.rs` changed from 7,029 to 5,613 lines. The point-cloud
contracts and pure identity helpers moved to `domain-pointcloud::commands`; the
1,148-line point-cloud command family and 82-line registration command family are
exported by their owning crates and expanded at two explicit composition points in
the `CanonicalAppRuntime` implementation. This preserves the method ABI and moves
journal/publish order, progress coalescing, cancellation checks, and store calls
verbatim.

For the step-5b families, the sidecar now holds only shared `CanonicalProjectStore`
state, imports the owner contracts, invokes the two owner command families, and
implements the surface document adapter. Surface execution itself delegates through
`SurfaceDocumentCommands`; it no longer accepts or imports `CanonicalAppRuntime`.

The remaining file includes the legacy route dispatcher, response conversion,
document/drafting commands (snapshots, bookmarks, viewing boxes, measurements, and
draw curves), generic import reconstruction/materialization, and its integration
tests. These are not point-cloud/surface/registration implementations. Dispatch must
stay until step 6, while the document/drafting and remaining IO families have no new
owner requested by this 5b cut. Their movement is intentionally not conflated with
this zero-behaviour domain extraction.

| Previous coupling                                               | Replacement                                                                                                                               |

The core `mesh_surface` and `registration` paths are forwarding re-export facades
over the owner source. They use a source facade instead of a Cargo dependency
because `core -> domain` would invert the enforced layering and create a cycle while
the old public paths still have consumers. The implementation has one physical
source owner in each domain crate; the facade can be removed when those consumers
move.

## 5b-fix

### Real foundation ownership

The two core source includes were removed. `himmelcad-model::surface` now owns the
neutral surface DTOs, constants, defaults, serde contracts, and typed error values;
`himmelcad-domain-surface::mesh_surface` imports and publicly re-exports those
contracts while retaining the surface algorithms and all of their tests. The old
`himmelcad_core::mesh_surface` path is only `pub use himmelcad_model::surface::*`.
The sidecar terrain bench now imports the algorithm from
`himmelcad-domain-surface` directly.

`himmelcad-model::registration` now owns every neutral registration contract:
recipes and methods, point-pair and ICP inputs/options, lifecycle and preview
values, stable errors, defaults and validation, and the origin/project-north and
similarity-to-placement/composition helpers. The underlying `WorldPoint`,
`Similarity3D`, `EmpiricalModelKind`, `PointResidual`, and `ResidualReport` value
contracts plus similarity application moved to `himmelcad-model::transform` and
are re-exported by `himmelcad-transform`, preserving their old paths and serde
shapes. `himmelcad-domain-registration` imports and publicly re-exports those
foundation contracts while retaining the fitting and ICP algorithms and all
tests. The old `himmelcad_core::registration` path re-exports only
`himmelcad_model::registration`; canonical IO imports that foundation module
directly. No foundation crate depends on either domain crate.

### Real domain command services

`himmelcad-document::domain_commands` defines `PointCloudDocumentCommands` and
`RegistrationDocumentCommands`, plus path-free residency/dataset views and the
existing publication progress shape. Their capabilities are limited to the
operations used by these services: live residency, verified CAS reads and
materialization, entity-version reads, JSON-object storage, journal transactions,
and atomic prepared-package publication.

`CanonicalAppRuntime` implements both traits over its existing
`CanonicalProjectStore`. The implementations are the composition adapter; the
point-cloud command logic is ordinary compiled code in
`himmelcad-domain-pointcloud::canonical_command_service`, and bounded committed
cloud sampling is ordinary compiled code in
`himmelcad-domain-registration::canonical_command_service`. The runtime keeps thin
methods with the prior names, parameters, return values, and error mapping. The two
`.inc.rs` files and both exported macros were deleted. Publication order,
cancellation boundaries, progress values, package contents, journal transactions,
and wire routes are unchanged.
