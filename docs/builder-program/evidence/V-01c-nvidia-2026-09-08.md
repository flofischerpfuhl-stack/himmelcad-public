# V-01c — Builder NVIDIA adapter selection — 2026-09-08

Status: **NVIDIA renderer selection COMPLETE; Class W qualification NOT
COMPLETE.** Builder's stable path on this laptop is hardware WebGL2 through
ANGLE Vulkan on the Quadro M2200. Quadro WebGPU adapter creation succeeds, but
WebGPU canvas presentation is invalid on the installed NVIDIA 580 / Electron
43 stack. The completed baseline is a severely contended Class-I diagnostic,
not a quiet Class-W result.

## Decision

On Linux, `HIMMELCAD_GPU=nvidia` now gives Electron these switches:

```text
--use-angle=vulkan
--enable-features=DefaultANGLEVulkan
--enable-unsafe-webgpu
--ozone-platform=x11
```

The environment variable is opt-in for ordinary Builder development; with it
unset, Electron's existing selection is unchanged. The baseline harness sets
the preference to `nvidia` by default, records that preference, and disables
Vite HMR only for its owned measurement process. It does not install a driver,
require an NVIDIA device, set PRIME variables, force an ICD, or reject a
machine merely because NVIDIA is absent.

`Vulkan` is deliberately not included in `--enable-features`. Enabling
Chromium's Vulkan compositor exposes a non-fallback WebGPU Quadro adapter, but
the first real surface present fails. With only `DefaultANGLEVulkan`, Chromium
reports its WebGPU adapter as a fallback adapter; the existing
`reliableAutomaticBrowserBackend()` therefore selects `webgl2`, and wgpu binds
the hardware ANGLE/Vulkan WebGL2 adapter.

The WebGPU failure is exact and repeatable. ANGLE first reports
`VK_ERROR_FEATURE_NOT_PRESENT` (`Internal Vulkan error (-8)`) in
`DmaBufImageSiblingVkLinux.cpp`. Dawn then rejects the canvas texture import:

```text
Requested allocation size (...) is smaller than the image requires (...)
at ImportMemory (.../MemoryServiceImplementationOpaqueFD.cpp:132)
```

The resulting texture, texture view and command buffer are invalid. Neither
ICD selection, PCI hints, disabling GPU-memory-buffer compositor resources nor
disabling the Vulkan surface fixes it. This is not a usable WebGPU present and
is not accepted merely because `requestAdapter()` succeeds.

The selected path was also verified in the actual Builder. Kernel diagnostics
reported:

```text
adapterName: ANGLE (NVIDIA, Vulkan 1.4.312 (NVIDIA Quadro M2200 (0x00001436)), NVIDIA)
backend: webGl2
driverInfo: WebGL 2.0 (OpenGL ES 3.0 Chromium)
```

At the same time, `nvidia-smi` attributed the Electron GPU process to the
Quadro (85 MiB during the focused check). GPU timestamp queries are unavailable
through this WebGL2 backend.

## Kernel negotiation and hardware class

Builder passes `backend="automatic"`. The TypeScript kernel first probes
`navigator.gpu.requestAdapter({ powerPreference: "high-performance" })`. A
browser fallback adapter causes an explicit `webgl2` choice; null/probe errors
leave Rust automatic selection in control. Rust automatic enables browser
WebGPU plus the permanent GL fallback and asks wgpu for a high-performance,
surface-compatible, non-fallback adapter.

V-01b fell to WebGL2 on Intel because default Electron exposed no usable
high-performance WebGPU adapter and Rust retained its GL fallback. The selected
V-01c switches expose only a fallback WebGPU adapter but a hardware NVIDIA
WebGL2 adapter, so the TypeScript guard deliberately chooses the latter. The
full Chromium Vulkan combination reaches Quadro WebGPU, but its first surface
present is invalid as documented above.

The completed Quadro session still resolves `hardwareClass: I`. WebGL2 reports
`deviceKind: other` and browser inventory supplies no GPU-memory size, so
`hardware_policy.rs` uses its 512 MiB `Other` fallback (307.2 MiB usable), below
the 1.5 GiB Class-W usable-memory floor. Its contended calibration also implied
approximately 0.87 GiB/s upload, 87.4 Mpoints/s, 131.1 Mtriangles/s and
21.8 Msplats/s, below the checked-in W floors of 2.0 GiB/s, 500, 250 and 150
respectively. No render policy or scheduling code was changed in V-01c.
